# JANUS HELIOS — Transaction Guardrails

> Negotiation framework only. A definitive transaction must be prepared/reviewed by qualified counsel for the governing jurisdiction.

## 1. Payment and control transfer

Recommended sequence:

```text
SIGNED DEFINITIVE AGREEMENT
        ↓
FUNDS PLACED IN AGREED ESCROW / CONFIRMED PAYMENT MILESTONE
        ↓
BUYER-CONTROLLED DESTINATION CREATED
        ↓
SOURCE / DOCUMENTATION / LISTED ASSETS TRANSFERRED
        ↓
OBJECTIVE ACCEPTANCE TESTS
        ↓
ACCEPTANCE CERTIFICATE
        ↓
ESCROW RELEASE / FINAL MILESTONE
```

Seller personal account credentials are never a delivery item.

An escrow release condition should be objective — for example, delivery of the listed assets matching the agreed manifest and acceptance criteria — rather than an undefined standard such as `buyer is commercially satisfied`.

## 2. No broad implied asset grab

A definitive agreement should use the Purchased Assets and Excluded Assets schedules. Avoid undefined phrases that could unintentionally transfer:

- the entire JANUS ecosystem;
- all future inventions;
- all seller know-how;
- all `related` or `derivative` technology;
- personal accounts;
- unrelated repositories;
- specialized child products not separately priced.

## 3. Warranties should match facts

Potential seller representations can be negotiated around facts that can actually be diligenced, such as authority to sign, disclosed contribution sources, disclosed third-party licences and lack of knowingly undisclosed encumbrances.

HELIOS transaction materials should **not** state or imply a warranty of:

- guaranteed profitability or revenue;
- guaranteed token appreciation;
- guaranteed data-center cost reduction;
- production readiness before the production gates are met;
- worldwide non-infringement without qualification;
- absence of every unknown security defect;
- regulator approval;
- future provider availability;
- casino/gambling certification.

Liability caps, indemnity scope, survival periods, knowledge qualifiers and baskets/caps are definitive-agreement issues for counsel and negotiation.

## 4. Prototype / production boundary

The current public HELIOS build is a capability/evaluation prototype. Acquisition of the code does not itself provide:

- real-money gambling approval;
- certified RTP/RNG/game math;
- production provider settlement;
- live compute-provider contracts;
- privacy/security certification;
- financial/crypto licences;
- measured data-center offload economics.

These can be separate workstreams or conditions for a later production deployment, but they are not hidden deliverables of a HELIOS-only source/IP sale unless expressly contracted.

## 5. Commercial economics boundary

Illustrative unit economics in HELIOS documentation are sensitivity examples. They are not forecasts or guarantees.

A buyer evaluating compute economics should rely on a sponsor/provider pilot measuring real:

- device-hours;
- watt-hours;
- verified work units;
- throughput/latency;
- retry and failure rate;
- provider settlement/value;
- cost per verified work unit.

## 6. Trademark and patent boundary

The repository currently makes no verified patent-status claim. A transaction must not describe HELIOS as patented or patent-pending without an actual filing record.

Use of names such as `JANUS HELIOS` should be treated separately from code ownership. Before assigning or relying on a mark, parties should conduct the appropriate trademark clearance/registration review for the intended territory and class.

A code/IP acquisition does not automatically transfer a registered mark unless that mark is expressly listed and assignable.

## 7. Provider relationships

Public references and outreach to providers/partners do not equal contracts or endorsements. A provider relationship is transferable only if an actual agreement exists, permits assignment or the counterparty consents as required, and the definitive transaction lists it as an assigned contract.

## 8. Security and credentials

At handover:

- revoke seller-controlled deployment/API secrets that are no longer needed;
- buyer creates new credentials in buyer-owned accounts;
- do not export personal recovery codes or MFA secrets;
- keep production provider secrets server-side;
- document credential rotation without putting secrets in Git.

## 9. Change-of-control / assignment review

Any actual third-party agreement that is proposed for transfer must be reviewed for assignment, change-of-control, confidentiality and consent restrictions before it is listed as a Purchased Asset.

## 10. No automatic non-compete

A HELIOS acquisition does not automatically prohibit the seller from working in software, distributed computing, games or related fields. Any non-compete/non-solicit restriction must be expressly negotiated, narrowly scoped, lawful in the governing jurisdiction and separately reflected in transaction value.
